INSTRUCCIONES PARA FIGMA - PRESENTECH

Objetivo:
Crear mockups de alta fidelidad para PresenTech, una aplicacion web mobile-first para docentes de colegios Fe y Alegria. El sistema permite iniciar sesion, consultar clases asignadas, revisar el calendario semanal, tomar asistencia e importar estudiantes desde Excel. La interfaz sera presentada al colegio como demostracion, por lo que debe verse formal, academica, confiable y lista para uso institucional.

Audiencia principal:
Docentes que usaran la aplicacion principalmente desde celular durante la jornada escolar. La experiencia debe ser rapida, clara, tactil y facil de operar con una mano. Priorizar pantallas de 375px, 390px y 430px de ancho. Luego adaptar a tablet y escritorio sin perder densidad ni claridad.

Filosofia visual:
- Mobile First.
- Tono academico, institucional y profesional.
- No usar emojis.
- No crear una landing page ni una pagina promocional. La primera experiencia debe ser la aplicacion funcional.
- Estilo sobrio, limpio y de trabajo diario, no marketing.
- La aplicacion debe sentirse confiable para un colegio: ordenada, legible, estable y serena.
- Usar tarjetas solo para elementos repetidos o bloques funcionales concretos. Evitar tarjetas dentro de tarjetas.
- Evitar decoraciones innecesarias, fondos con blobs, orbes, degradados excesivos o ilustraciones genericas.

Paleta recomendada:
- Azul institucional oscuro: #1E3A5F.
- Azul de accion principal: #2563EB.
- Blanco: #FFFFFF.
- Fondo claro: #F4F7FB o #F8FAFC.
- Texto principal: #172033.
- Texto secundario: #667085.
- Bordes suaves: #D9E2EF o #CBD5E1.
- Verde para presente/exito: #166534, fondos #F0FDF4.
- Rojo para ausente/error: #B42318 o #991B1B, fondos #FEF2F2.
- Naranja para atrasado/advertencia: #9A3412, fondos #FFF7ED.

Tipografia:
- Usar una tipografia sans-serif moderna, clara y sobria.
- Jerarquia compacta: titulos claros, subtitulos breves, contenido facil de escanear.
- Evitar textos gigantes fuera de contexto. En mobile, priorizar legibilidad y espacio vertical.
- No usar letter spacing negativo.

Componentes base que deben aparecer en el diseno:
1. Button:
   - Variantes primary, secondary y danger.
   - Estados normal, hover, disabled y loading.
   - Botones tactiles con altura minima aproximada de 40px.
   - Usar iconos simples cuando ayuden a reconocer la accion: cerrar sesion, guardar, actualizar, subir archivo, volver.

2. Input:
   - Campo de texto.
   - Campo de contrasena.
   - Campo de fecha.
   - Estados normal, focus y error.
   - Labels visibles, claros y en espanol.

3. Spinner:
   - Indicador de carga discreto.
   - Debe funcionar dentro de botones y en paneles de carga.

4. Modal:
   - Confirmaciones para acciones importantes.
   - Usos: guardar asistencia, actualizar asistencia, importar estudiantes.
   - Debe ser claro, con acciones primarias y secundarias.

5. Badge:
   - Estados: Presente, Ausente, Atrasado.
   - Usar color semantico consistente.

Layout general:
- Header superior fijo o sticky en pantallas autenticadas.
- Header debe mostrar:
  - Marca: PresenTech.
  - Titulo de la seccion actual.
  - Nombre del docente autenticado.
  - Boton de cerrar sesion.
- Bottom navigation en mobile.
- Bottom nav debe incluir:
  - Pruebas o Inicio tecnico, si se mantiene para demo interna.
  - Clases.
  - Calendario.
  - Asistencia.
- En escritorio, el contenido puede tener ancho maximo centrado, con layout mas amplio y mejor uso horizontal.

Flujo principal:
Login -> Clases -> Calendario semanal -> Toma de asistencia.

Pantalla 1: Login docente
Ruta esperada: /login.
Objetivo: Permitir autenticacion con correo institucional y contrasena.
Elementos:
- Marca PresenTech visible.
- Titulo: Acceso docente.
- Texto breve de apoyo: acceso al modulo docente.
- Input de correo institucional.
- Input de contrasena.
- Boton principal: Ingresar.
- Mensaje de error visible si las credenciales fallan.
Estilo:
- Pantalla centrada, limpia, formal.
- En mobile, formulario de ancho completo con margenes laterales comodos.
- No sobrecargar con imagenes decorativas.

Pantalla 2: Mis clases
Ruta esperada: /clases.
Objetivo: Mostrar las clases asignadas al docente autenticado.
Datos a representar:
- Materia.
- Nombre del paralelo.
- Proxima clase.
- Horarios semanales.
- Accion para ver calendario.
- Accion para importar estudiantes por clase/paralelo.
Componentes:
- Header con docente.
- Grid/lista de ClaseCard.
- Cada ClaseCard debe mostrar materia como dato principal.
- Paralelo como dato secundario.
- Bloque pequeno de "Proxima clase".
- Chips o filas compactas para horarios.
- Boton "Ver calendario".
- Boton "Importar Excel".
Mobile:
- Cards apiladas en una columna.
- Botones grandes y faciles de tocar.
Desktop:
- Grid de 2 o 3 columnas.

Pantalla 3: Importacion de estudiantes
Esta accion ocurre desde una clase.
Objetivo: Cargar estudiantes desde un archivo Excel.
Flujo:
- Boton "Importar Excel".
- Seleccion de archivo .xlsx o .xls.
- Modal de confirmacion mostrando cantidad de estudiantes detectados.
- Vista preliminar de algunos nombres.
- Boton "Importar".
- Mostrar error si el archivo no contiene columnas validas.
Columnas esperadas:
- nombres.
- apellidos.
Tono:
- Advertir que la importacion reemplaza la matricula activa del paralelo.
- Mensaje formal y claro, sin alarmismo.

Pantalla 4: Calendario semanal
Ruta esperada: /clases/:id/calendario.
Objetivo: Mostrar los horarios semanales de una clase seleccionada.
Datos a representar:
- Materia.
- Paralelo.
- Lista lateral o superior de horarios.
- Calendario semanal con bloques de clase.
Comportamiento:
- Al tocar un bloque de clase, navegar a la toma de asistencia de ese horario y fecha.
Mobile:
- Calendario debe ser legible en pantalla pequena.
- Si la vista semanal es muy densa, permitir bloques verticales por dia o una lista semanal equivalente.
- Priorizar que el docente toque rapidamente el horario correcto.
Desktop:
- Puede mostrarse como calendario semanal completo.

Pantalla 5: Toma de asistencia
Ruta esperada: /asistencia/:idHorario/:fecha.
Objetivo: Registrar o editar la asistencia de una sesion de clase.
Datos a representar:
- Materia.
- Paralelo.
- Fecha.
- Indicador si es nuevo registro o modo edicion.
- Resumen: X presentes, Y ausentes.
- Observaciones generales de la sesion.
- Lista de estudiantes.
Por cada estudiante:
- Nombre y apellido.
- Estado actual con badge.
- Acciones: Presente, Ausente, Atrasado.
- Si se marca Atrasado, mostrar campo Justificativo obligatorio.
- Campo opcional de observaciones del estudiante.
Accion principal:
- Guardar asistencia o Actualizar asistencia.
- Antes de guardar, mostrar modal de confirmacion con resumen.
Reglas:
- Atrasado cuenta como presente.
- Atrasado requiere justificativo.
- Si ya existe asistencia para ese horario y fecha, mostrar indicador claro de modo edicion.
Mobile:
- Lista vertical de estudiantes.
- Botones segmentados grandes para Presente/Ausente/Atrasado.
- Resumen siempre facil de ver antes de guardar.

Pantalla 6: Estados vacios y errores
Crear variantes para:
- No hay clases asignadas.
- No hay estudiantes activos.
- Error al conectar con backend.
- Cargando datos.
- Sesion no autenticada redirige a login.
El tono debe ser claro y tranquilo.

Pantalla 7: Vista tecnica opcional de pruebas de endpoints
Actualmente existe una pantalla inicial para probar endpoints.
Para la demo al colegio, esta pantalla no debe ser protagonista.
Si se conserva, debe verse como panel interno o herramienta tecnica, no como flujo principal del docente.
El flujo publico de demo debe iniciar en Login y luego ir a Clases.

Endpoints existentes que sustentan la interfaz:
- POST /api/v1/auth/login
- GET /api/v1/clases/mis-clases
- GET /api/v1/clases/{id}/horario
- GET /api/v1/clases/{id}/estudiantes
- POST /api/v1/estudiantes/importar/{idParalelo}
- GET /api/v1/asistencias/{idHorario}/{fecha}
- POST /api/v1/asistencias
- PUT /api/v1/asistencias/{id}

- components/common:

  - Modal.
  - Spinner.

  - CalendarioSemanal.
- components/asistencias:
  - AsistenciaItem.
  - AsistenciaForm.
- components/estudiantes:
  - ImportarExcelButton.
- pages:
  - LoginPage.
  - ClasesPage.
  - CalendarioPage.
  - AsistenciaPage.

Requisitos de experiencia mobile:
- Disenar primero para 375px.
- Revisar tambien 390px y 430px.
- Botones tactiles comodos.
- No depender de hover para acciones importantes.
- Evitar tablas anchas en mobile.
- Usar listas, cards funcionales y controles segmentados.
- Bottom nav visible y comoda.
- Header compacto.
- Evitar texto largo en botones.
- El contenido no debe solaparse ni salirse de pantalla.

Requisitos de accesibilidad:
- Contraste suficiente en textos y botones.
- Labels visibles en formularios.
- Estados de error claros.
- Iconos acompanados por texto cuando la accion no sea obvia.
- Tamanos tactiles adecuados.

Generar mockups mobile-first de alta fidelidad para:
1. Login docente.
2. Mis clases.
3. Importar estudiantes desde Excel.
4. Calendario semanal de una clase.
5. Toma de asistencia nueva.

Tambien generar, si es posible:

- Componentes reutilizables con variantes.

- Guia breve de estilos.
- Flujo navegable entre pantallas.

Prioridad final:
La interfaz debe comunicar que PresenTech es una herramienta academica seria, moderna y simple para que docentes de Fe y Alegria tomen asistencia desde el celular con rapidez y confianza.
